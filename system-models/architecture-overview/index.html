Delos: how the system is put together

This page goes one level below the spec. It covers the main parts of the running application and how they connect, not individual operators or algorithms. Each part has a hierarchical name, such as Interface.DisplayResolver or Filesystem.Projects. The first half is the layer it belongs to and the second half is the part itself. The two main loops

Edit → see the result

  1. You change something in Interface.Views, such as dragging a handle or a slider.
  2. Interface.State applies the change to the Document.Graph graph and records an undo step. A continuous drag counts as one step.
  3. Interface.DisplayResolver works out what the image view should show and which controls to draw over it.
  4. Workers.Background gets a preview job and drops any older job that is still running.
  5. Engine.Evaluator pulls just the visible region at screen resolution through the Document.NodeKinds node kinds. Their Engine.Kernels kernels run on Engine.Backends and sample Engine.Sources.
  6. The finished frame goes back to Interface.Views.

Change → saved project

  1. Any change to the graph in Interface.State triggers autosave in Interface.Sessions. This only happens in project mode; quick mode saves nothing.
  2. Workers.Background gets a snapshot of the graph and the images it knows about.
  3. Document.Expressions turns the graph into text. Filesystem.Projects writes it atomically and updates inputs/: it copies in new images and moves images that are no longer used to a session folder, so undo can still restore them.
  4. The status bar shows the result as Saving… or Saved.

Components

Interface · user interface

Interface.Views

The visible parts of the app: the graph editor, the image view with its on-canvas controls, the inspector (parameter forms) and dialogs (export, size conflicts, project prompts). The forms and controls are not written separately for each operator. They are generated from what each Document.NodeKinds node kind declares.

src/ui/graph_view.rs, image_view.rs, inspector.rs, dialogs.rs

Interface.DisplayResolver

Decides what the image view shows: the output, a relocated output, or the selected operator's output or input. It also decides whether the view stays fixed and which node's controls are drawn. It chains the coordinate mappings of the nodes in between, so an upstream node's controls land in the right place even after Clip or Resize. This covers spec §3.2–3.3. It also picks what "Export" exports.

App::displayed() in src/ui/state.rs, using Graph::space_map

Interface.Sessions

Handles quick mode versus project mode, the "create a project?" question on the first import, opening, closing and sharing projects, and autosave. Every action is a plain function of the app state. The end-to-end tests call the same functions the UI does, without opening a window.

src/ui/session.rs

Interface.State

The single shared state: graph, selection, view settings, undo/redo history and export status. It is stored as reactive signals, so the UI updates when they change. All changes go through edit, and continuous drags go through edit_coalesced. Each change starts a new preview and an autosave.

src/ui/state.rs

Workers · background work

Workers.Background

Keeps slow work off the UI thread. Previews run on a dedicated thread: when a newer request arrives, the older render is abandoned. The worker also decodes imports, runs exports with progress and cancellation, and creates, opens, saves and shares projects. Results go back to the UI as messages, such as Frame, ExportProgress and ProjectSaved. On the web, which has no threads, the same jobs take turns on the main thread.

src/worker.rs

Engine · rendering

Engine.Evaluator

Rendering is demand-driven. The shown node gets a request: a region in its own coordinate space and a pixel grid to fill. The node asks its inputs for exactly what it needs, and so on up the graph. A preview asks for a screen-sized grid and an export asks for full-resolution bands. Because of this, preview cost depends on the window size, not the image size. Ordinary node results are not cached; only expensive ones are, such as background-removal masks.

src/engine/mod.rs, geom.rs, cache.rs

Engine.Kernels

The per-pixel building blocks that node kinds call, such as blend, invert and sampling. Each one is written twice, in WGSL for the GPU and in Rust for the CPU, with the same parameters, so both backends give matching results.

src/engine/kernels.rs

Engine.Backends

The GPU backend uses wgpu compute shaders. Shaders are compiled the first time they are used, intermediate results stay on the GPU between steps, and textures are reused. If no GPU is available, the CPU backend runs the same kernels in parallel with rayon. Data moves between steps as tiles: premultiplied RGBA, stored on either the CPU or the GPU.

src/engine/gpu.rs, pool.rs, tile.rs

Engine.Sources

Each imported image is decoded once into a mip pyramid, a set of copies at smaller and smaller scales, so any region at any zoom is cheap to read. Pyramid levels are uploaded to the GPU in the background and kept there within a memory budget. Until a level is on the GPU, the CPU path is used, so rendering never waits for an upload.

src/engine/source.rs, resident.rs

Document · the edited image

Document.Graph

The document itself. Each node stores its own inputs as links to an output of another node, which is how split nodes with several outputs are referenced. The graph answers structural questions: each node's size (generators have none), whether a chain of Stack nodes should be shown as a layer stack, where a Resize node needs to go after a size conflict, and how coordinates map between two nodes.

src/graph.rs

Document.NodeKinds

Each operator and generator implements the NodeKind trait and is added to a registry. The trait covers its ports and outputs, parameters, size rule, rendering, on-canvas controls, whether it is edited on its input or its output, and how its coordinates map to its inputs. To add an operator, you implement the trait and add it to the registry.

src/nodes/mod.rs, basic.rs, generators.rs, resize.rs, split.rs, bgremove.rs

Document.Expressions

Converts between the graph and Delos expressions, the Lisp-like text stored in project.delos. Nodes used more than once are bound with def, and stack chains are written as (stack …). Every parameter is written out, including defaults. Parse errors give a line and column.

src/expr.rs

Filesystem · files on disk

Filesystem.Codecs

A list of codecs used for both import and export. An export pulls the image from the graph one horizontal band at a time. The PNG codec writes each band to the file as it arrives, so even a 16K export uses a bounded amount of memory.

src/formats.rs

Filesystem.Projects

A project is a directory containing project.delos and inputs/. Saves write a temporary file and then rename it into place, so a half-written file is never left behind. inputs/ always holds exactly the images the graph uses. Before opening, the store checks the project's structure, and it rejects any path that points outside the project. It also packs and unpacks .delosproject zip files.

src/project.rs
