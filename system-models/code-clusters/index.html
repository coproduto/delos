Delos code clusters

I built an item-level reference graph of the delos crate and partitioned it into groups that reference each other heavily and the rest of the code rarely. The resulting clusters often cut across files and directories. They show which code really moves together, where the seams are, and which parts can be reviewed as black boxes.

What the clusters say

  1. Clusters describe the code's real structure better than its file layout. The 12 clusters keep 80% of references internal (modularity 0.67). The 30 files keep only 55% (0.48), and the 4 top-level directories keep 78% (0.51), even though they are three times coarser. Files are too fine and directories mix concerns.
  2. NodeKind is a cross-cutting seam, not a module. The trait's methods spread over five clusters by role. name/category/inputs/size/input_map belong to C0, params/overlays to C3, render/render_output to C4, edit_view/outputs to C1 and id to C9. Each kind's impl splits the same way. Adding a node kind is therefore a change to four or five clusters even though it touches only one file. Review it as a cross-cutting change.
  3. Export is the cleanest feature slice. C6 runs top to bottom: codecs and banded rendering in formats.rs, Worker::export, ExportDialog, ExportState and the platform save-target picker. Export changes can be reasoned about inside one cluster, even though it spans five files and three layers.
  4. Four clusters are near black boxes. Blend-mode math (0.97), GPU residency (0.86), the GPU backend (0.82) and the CPU kernels (0.77) have narrow interfaces. Humans can review these at the boundary, for example "does the Kernel table still mean the same thing?", rather than line by line.
  5. Decisions ripple through the low-cohesion clusters. The Node kind catalogue (0.57), Worker/sources/projects (0.58), App shell (0.63) and Graph document (0.64) leak most. The heaviest seam in the system is C1 ↔ C2 (197 refs), where the app shell edits the graph. Next come C0 ↔ C1 (106), C0 ↔ C3 (96) and the UI ↔ worker message channel C2 ↔ C8 (95, through Msg and pump).
  6. Several files hold two or three concerns. engine/source.rs splits into storage and pyramids (C8, with projects) and rendering (C4). expr.rs splits into printing (C1, with the graph) and parsing (C9). engine/kernels.rs splits three ways: CPU kernels (C7), blend math (C11) and WGSL assembly (C5). ui/state.rs splits into shell state (C2), graph actions (C1) and export state (C6). These are natural split points if those files grow.
  7. Some UI code clusters with its domain, not with ui/. The graph editor (graph_view.rs, NodePanel, LayerStack) belongs to the graph document. The parameter form (ParamField) belongs to the parameter schema. Only the shell, the canvas view and session handling form a "UI" cluster.

Method

Reference graph. rust-analyzer scip produced a semantic index of the crate with the default desktop feature set, so references are compiler-resolved rather than text matches. Each top-level item is a node: functions, structs, enums, traits, constants, statics, and methods as Type::method. Fields, variants and std-trait impls (Display, PartialEq, …) are folded into their type. Each reference inside an item's body adds weight to an edge from that item to the target. use lines are ignored. Two kinds of structural edge are added: method → its type (weight 2) and trait-impl method → trait method declaration (weight 1). #[cfg(test)] code and tests/ are left out of the graph.

Clustering. Louvain community detection on the undirected graph uses edge weight 1 + ln(references), which damps hot loops that repeat one call many times. A resolution sweep from 0.4 to 2.0 showed a flat modularity plateau (0.67) from 0.8 to 1.5. Resolution 1.0 was chosen, and the best of 30 seeds is reported. On average 96% of edges have their endpoints assigned the same way (together or apart) across seeds. Raw weights give a similar picture (Q = 0.70, 15 clusters).

Regions. At resolution 0.4 the algorithm finds 7 coarse groups. Five are clean merges of the clusters above: C0+C3, C1+C9, C4+C7, C5 alone and C11 alone. The other two are not. App shell and export (C2+C6) take the worker and project half of C8, and residency (C10) takes the SourceImage half of C8. C8 is the only cluster that splits at the coarse level, which marks it as the least settled boundary.

Naming. Cluster names and tags are mine. They come from each cluster's highest-degree members, its file composition and the module doc comments, and they are recorded in data/cluster-names.json.

Caveats. Web-only (cfg(feature = "web")) code paths aren't indexed. References inside rsx! are included as far as rust-analyzer resolves them. Dynamic dispatch through &dyn NodeKind appears as references to the trait method, connected to each implementation by the trait-impl edges. Line counts are summed item spans, so they are approximate.
