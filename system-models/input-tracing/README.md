# Delos input traces

A model of Delos built by **tracing every way input enters the program** and
following each one to where it ends: a changed document, a render, a file
on disk, or a message back on screen. The thesis being tested: *the best
way to understand a project's structure is to trace how each input path
works.*

The analysis is of commit `197e30c`. Nothing in `src/` or `tests/` was
changed.

## What counts as input

| Channel | Count | Where it enters |
|---|---|---|
| Pointer, keyboard and form events (rsx `on…` handlers) | 105 | `src/ui/*.rs` |
| Native dialogs whose answers flow back (file/folder pickers, confirm) | 5 | `src/ui/platform.rs` |
| Files read from disk (images, `project.delos`, `.delosproject` archives, `inputs/`) | 14 | `worker.rs`, `project.rs`, `session.rs` |
| Environment variables | 8 reads, 5 names | `gpu.rs`, `project.rs`, `bgremove.rs`, `platform.rs` |
| The webview itself (device pixel ratio, frame requests) | 2 | `src/ui/platform.rs` |
| Reactive effects: not inputs themselves, but the place where every edit turns into work | 6 | `image_view.rs`, `session.rs`, `mod.rs` |

The full list, with each entry's handler, the functions it calls and the
signals it writes, is in [inventory.md](inventory.md) (machine-readable:
[inventory.json](inventory.json)). Both are generated by
`system-analysis-tools/input-tracing/inputtrace`.

## The one-paragraph model

Every UI input mutates **signals on one `App` struct**
([state.rs:109](../../src/ui/state.rs#L109)). Document changes go through
`App::edit` or `App::edit_coalesced`, which snapshot the graph for undo.
Nothing renders or saves in direct response to an input. Instead, **five
effects** subscribe to those signals and hand work to a **background
`Worker`**: the preview effect and autosave are the important ones. The
worker answers with **`Msg`s on one channel**, and a single `pump` applies
them back to `App` signals. Inputs from disk, the environment and native
dialogs join this same loop at known points. So nearly every trace has the
same shape:

```
event ─▶ handler ─▶ App method ─▶ signal write ─▶ effect ─▶ Worker (thread) ─▶ Msg ─▶ pump ─▶ signal write ─▶ re-render
```

[00-spine.md](00-spine.md) describes that loop once, so the traces can be short.

## How to read a trace

Each trace is a numbered path. A step names what happens and cites the
code as `path:line`. Arrows mark hops that a call graph would not show:

- **⇢ effect**: a signal write reruns a subscribed effect (Dioxus
  reactivity);
- **⇢ thread** / **⇢ task**: work moves to a background thread or an async
  task;
- **⇢ Msg::X**: the worker answers on the channel, and `pump` handles it.

Each file ends with **Decisions**: places where the trace shows a choice
that a human should own.

## Reproduce and keep it honest

```sh
T=system-analysis-tools/input-tracing/inputtrace
$T inventory . --md system-models/input-tracing/inventory.md --json system-models/input-tracing/inventory.json
$T trace . src/ui/mod.rs:351          # the toolbar Import button, end to end
$T signals .                          # who writes each signal, which effects rerun
$T channels .                         # Msg variants: senders and receivers
$T coverage . system-models/input-tracing   # entry points no trace cites
```

`coverage` exits non-zero when an entry point (handler, effect, env read,
dialog, webview hook) has no `path:line` citation in these documents. It
passes on this commit. Rerun it after UI changes to find inputs that have
no trace yet.

## Does tracing input explain the structure? (assessment)

**What it showed well.**

- **The architecture is one loop.** Within a few traces it was clear that
  Delos has one state hub (`App`), one way to change the document (`edit`),
  one rendering path (the preview effect), one persistence path (the
  autosave effect) and one return channel (`pump`). Listing the modules
  shows none of that. Tracing input does.
- **Where the edges are.** The thread and async hops are exactly where
  concurrency bugs can live. The traces name each one, and what crosses
  it: snapshots of the graph, never references.
- **Who bypasses the rules.** The signal map shows three writers of
  `App.graph` outside `edit`. All three findings about undo, autosave and
  canvas size come from those bypasses or from `edit`'s own bookkeeping. An
  input view finds these naturally, because it asks "what does this event
  change?" for every event.
- **Where validation lives.** It is at the input sites, and it differs
  between paths (see findings).

**What it showed poorly.**

- **The engine is a black box.** Every input that renders ends in
  `render_to_cpu`, so input tracing says nothing about tiling, GPU/CPU
  dispatch or the node kinds' coordinate maps. The code-clusters and
  invariants models cover that part much better.
- **Static tracing over-approximates.** The tracer ignores `cfg` gates and
  branches, so it shows paths that *may* run. The traces here were written
  by reading each branch. The tool's output is a map to check, not the
  answer.
- **Reactive edges are invisible to ordinary tools.** In Dioxus the most
  important hop (signal write → effect) is not a call. The tool models it
  (it treats `.read()` as subscribing and `.peek()` as not). Without that,
  input traces stop at "writes `App.graph`", which explains nothing.

Overall, input tracing explains the **application layer** (UI, session,
worker, persistence) better than any other view tried so far, and it found
real bugs there. It needs a second view for the computational core.
